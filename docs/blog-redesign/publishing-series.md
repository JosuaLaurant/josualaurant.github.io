# 블로그를 만드는 과정을 글로 남기는 계획

## 연재 원칙

블로그 구축 글은 제품 홍보가 아니라 **결정과 검증의 기록**으로 쓴다. 따라서 각 글에는 아래를
분리해 적는다.

1. 당시 문제와 제약
2. 고려한 선택지와 제외 이유
3. 실제 구현 범위
4. 검증한 동작과 아직 검증하지 않은 경계
5. 다음 글에서 다룰 결정

설계 문서를 그대로 공개 글로 복사하지 않는다. 독자가 재현할 수 있는 맥락, 필요한 코드 조각,
전환 과정의 실패·수정만 골라 새 글로 쓴다.

## 시작 글 후보

| 순서 | 가제 | 공개 가능한 핵심 |
| ---: | --- | --- |
| 0 | 오래된 GitHub Pages를 한 저장소 블로그로 다시 설계한 이유 | Hugo source/정적 결과가 갈라진 상태, 단일 저장소로 바꾼 기준 |
| 1 | 기술 블로그에 Astro를 고른 이유: 넣은 것보다 뺀 것 | Markdown, 정적 build, GitHub Pages와 v1에서 제외한 CMS·댓글·검색 |
| 2 | GitHub Pages를 branch 배포에서 Actions artifact 배포로 옮기는 법 | workflow 권한, lockfile, preview와 rollback 원칙 |
| 3 | Markdown frontmatter가 기술 글의 품질을 지키는 방식 | 제목·설명·태그·draft 검증과 RSS/sitemap 연결 |
| 4 | 첫 성능 개선 글을 어떻게 검증 가능한 이야기로 만드는가 | 전후 측정, 동일성 검사, 표본·한계 공개 방식 |

## 작업 기록과 연결하는 방식

기술 글은 ‘도구가 좋아졌다’는 결론부터 쓰지 않는다. 아래 문장을 출발점으로 삼는다.

```text
문제 → 측정 조건 → 가설 하나 → 변경 → 결과와 회귀 검사 → 채택/기각 이유 → 남은 한계
```

예를 들어 반복 초기화 제거 글은 시간 단축 수치와 함께, 입력·출력이 같았다는 동일성 검사를 적는다.
반대로 일부 지표만 좋아진 후보는 왜 안전한 개선으로 채택하지 않았는지를 중심으로 쓴다.

## 글 발행 전 체크

- 제목과 description만 읽어도 독자가 얻을 내용을 알 수 있는가?
- 전후 수치에는 workload, 표본, 장비·실행 조건을 적었는가?
- 성공한 결과만 남기지 않고 안전 gate·실패 사례·미확인 한계를 적었는가?
- 비공개 이미지·데이터·경로·서버 정보를 합성 자료나 일반화된 도식으로 바꿨는가?
- 코드 블록은 실행 단위로 충분하지만, 내부 프로젝트 전체를 공개하지 않아도 이해되는가?
